# ADR-0053: ADR-0017の注入の入口: 候補注釈とアプリ状態feedによる達成判定

- 日付: 2026-10-04
- 状態: 採択
- 決定者: yo-xe + Claude Code

## 背景

ADR-0017は、アプリ固有の手段で得た情報を外から注入すると決めたが、入口は未設計だった。Unityではdropdownの
正解候補が見えているのに初手で選べず、Blenderでは操作が届いても達成を確かめられず`unverified`で返っていた。
入口案は相談(`docs/consult/20261004-1326-adr0017-injection-entry-topic-20261004.md`)で絞り、EXP-0015で計測した。

## 決定

1. **A 候補注釈**: run requestの`app_annotations=[{match:{text}, role, name, value, source}]`。run初回観測で、正規化labelの
   完全一致が1領域(subject+rect)に限られる時だけ、その領域の全候補の`attributes["app"]`へ付す。候補の追加・操作種別・
   配送確認は変えない。同一OCR行のclick/fill両候補は同じ部品なので、操作種別でなく領域で数える。
2. **D 状態照合**: goalの`app_expect={source, key, equals}`。外側が用意したアプリ状態feed(JSON、書込時刻`t`付き)を操作後に読み、
   操作0.3秒後以降に書かれた値が一致した時だけ`outcome_verified`とする(最大2秒待つ)。不一致・古い・欠落は判定せず、
   既存の判定へ戻す。外側の成功申告ではなく、アプリが書いた実値を照合する。
3. feedと注釈の真正性はFinitactが確かめない。外側とアプリ側pluginの責任で、受容制約として公開文書に記す。

EXP-0015の結果(誤判定・誤操作は全条件0):

| 入口・case | goal文 | 注入なし→あり |
|---|---|---|
| D・Blender workspace | manifest | `verified_success` 0/5→5/5、中央値9.7→5.2秒、Jev呼出10→3 |
| D・Blender mode | 外側の書き直し(2goal) | `verified_success` 1/5→3/5、oracle 2/5→3/5 |
| D・負例(未達) | manifest、行動予算1 | `verified_success` 0/5 |
| A・Unity 2case | manifest | 1/5→5/5、2/5→3/5 |
| A・Unity 2case | 外側の書き直し | 5/5→5/5、5/5→5/5 |

Aは外側が具体的なgoalを書けば上積みが無いが、誤操作を増やさないため残す(yo-xe)。

## 検討した代替案(没案)

- **B 注入要素を候補として追加し画素・hit-testで再検証**: 今回の失敗は候補欠落でなく選択の停止で、主因に対応しない。
  画素とhit-testは位置の存在しか裏付けず、操作可否を根拠なく付けたADR-0030の経緯を繰り返す(相談)。
- **C 外側が選んだ要素を一意照合して直接実行**: 一意に照合できることとgoalに合うことは別。効果はref往復の削減で、
  既存のgoal `ref`(ADR-0041〜0043)と重なる(相談)。
- **Dで外側の成功申告をそのまま`verified_success`にする**: 判定の根拠が外側の主張になる。実値照合に限った(相談)。
- **Aの一意性を操作種別込みで数える**: 同一OCR行のclick/fillで常に曖昧になり、Unityで注釈が付かなかった(EXP-0015 smoke)。

## 影響

- `run_windows`入力に`app_annotations`、goalに`app_expect`が加わる(`finitact/runs.py`・`finitact/mcp_server.py`)。
- 注入源の例(Unity Editor書き出し・Blender feed)は`scripts/`に置き、製品には含めない。
- 仕様・`docs/decisions*.md`・`docs/known-issues*.md`へ反映する。ADR-0017は追記1で本ADRを参照する。
- Dの無いgoal(dropdownを開く等)の完了判定は約0.5で割れたまま残る(EXP-0015 mode g1)。
